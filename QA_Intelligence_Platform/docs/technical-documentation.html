What is this?

QA Intelligence Platform is a knowledge-first AI system built for QA engineering teams. It is not a chatbot bolted onto a code repo. It models the entire QA knowledge graph — frameworks, test cases, bug histories, PRDs, CI logs, meeting decisions — as first-class indexed objects across 10 purpose-built vector collections.

The platform's design principle: Chat is one interface. The Knowledge Layer is the product. Every feature (chat, RCA, RTM, coverage analysis, flaky-test detection) routes through the same retrieval pipeline and shares the same citation trail.

Design principle enforced in code: No route handler is allowed to call Qdrant or an LLM SDK directly. All intelligence flows through RetrievalEngine.retrieve(). This is documented in CLAUDE.md and enforced at review.

Knowledge Layer

All intelligence flows through backend/knowledge/retrieval_engine.py. This is the single callsite every feature uses — chat, search, RCA, RTM, coverage.

Pythonbackend/knowledge/retrieval_engine.py
class RetrievalEngine:
    def retrieve(self, query: str, metadata_filters=None, top_k=None) -> RetrievalResult:
        # 1. Route query to correct collection(s)
        classification = self._classifier.classify(query)
        # 2. Expand abbreviations + domain synonyms
        expanded_query   = self._expander.expand(query)
        # 3. Dense vector + BM25 sparse → RRF fusion
        raw_chunks       = self._searcher.search(
            expanded_query, classification.collections, top_k, metadata_filters
        )
        # 4. Cross-encoder rerank (bge-reranker-large)
        reranked         = self._reranker.rerank(query, raw_chunks, self.rerank_top_k)
        # 5. Trim to 6,000-token budget
        compressed       = self._compressor.compress(reranked)
        return RetrievalResult(
            chunks=compressed,
            intent=classification.intent,
            collections=classification.collections
        )

SHA-256 Incremental Indexing

Each chunk is hashed before embedding. The index_registry SQLite table stores (collection, sha256) pairs. Re-indexing a changed file only re-embeds the modified chunks — a 5,000-TC CSV re-ingest after adding 10 rows embeds 10 chunks, not 5,000.

Embedding — BAAI/bge-m3

570MB multilingual model producing dense (1024-dim) + sparse + multi-vector from one forward pass. Dense vectors go to Qdrant; the BM25-equivalent sparse representation combines with them in hybrid search via Reciprocal Rank Fusion.

FastAPI Gateway

Thin HTTP boundary: validate inputs (Pydantic), authenticate, rate-limit, delegate to Knowledge Layer. Zero business logic in routes.

Environment loading order matters: load_dotenv() must execute at the top of main.py before any import that reads config. A module reading an env var at import time sees an empty string if dotenv hasn't run yet — this caused silent LLM auth failures during early development.

On startup

  • init_db() — creates SQLite tables (users, sessions, index_registry)
  • ensure_collections() — creates any missing Qdrant collections with correct vector params
  • get_embedder() — pre-loads bge-m3 into memory (singleton via @lru_cache)

Retrieval Pipeline

Hybrid Search with RRF

Dense Qdrant search and BM25 sparse search run in parallel for each target collection. Reciprocal Rank Fusion merges the ranked lists: score = Σ 1 / (60 + rank_i). Dense embeddings give semantic recall; BM25 preserves exact keyword matches critical for JIRA IDs, function names, and TC codes.

Cross-Encoder Reranking

The top 10 chunks from hybrid search pass through BAAI/bge-reranker-large — a joint encoder that scores each (query, chunk) pair together, far more accurate than bi-encoder similarity for precision ranking. Top 5 survive for context assembly.

Why two-stage retrieval? Bi-encoder embeddings optimize for recall — they efficiently retrieve 10 plausible candidates from 100,000 vectors. Cross-encoders optimize for precision — they pick the best 5 from 10 candidates. Using both gives sub-100ms total latency with accuracy close to a pure cross-encoder sweep.

LLM Router

Sequential fallback chain with automatic muting. On quota/rate errors (429/503), the provider is muted for 60 seconds and the next is tried. Auth errors propagate immediately (no retry).

Engineering Decisions

🗂️
10 specialized collections instead of 1 general collection + metadata tags
A single collection forces every query to scan all vectors. 10 collections let the intent classifier direct retrieval to 1–3 relevant ones, reducing latency and noise. The tradeoff is higher setup complexity, managed by the CollectionSchema dataclass system.
📦
Renamed collections/ → collections_module/
A folder named collections/ in the Python path shadows the built-in collections module, causing cryptic import failures deep in pandas and SQLAlchemy. Renaming resolved it without changing the public API.
⚙️
Python 3.11 over system Python 3.9
macOS system Python 3.9 crashes in runpy when creating venvs with certain Homebrew paths. Pinned to /opt/homebrew/bin/python3.11.
🎨
Tailwind config as .js not .ts
Tailwind v3's PostCSS plugin reads the config via Node require(). A .ts file requires transpilation that doesn't happen automatically in Next.js 15's build pipeline, silently dropping all utility classes from the output CSS.
🔄
Qdrant Docker image version must match client
The Qdrant Python client 1.18.0 warns (and may error) when the server version differs by more than one minor version. Updated Docker image from v1.9.2 to v1.13.6 to match.
🤖
Groq model: llama-3.3-70b-versatile
llama-3.1-70b-versatile was decommissioned by Groq. The 404 error surfaced as a silent LLM failure — no stacktrace, no useful log. Now logs a warning on every provider fallback to make failures debuggable.
